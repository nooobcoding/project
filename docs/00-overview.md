# 코인 자동매매 프로그램 — 프로젝트 개요

## 1. 프로젝트 소개

| 항목 | 내용 |
|---|---|
| 이름 | 코인 자동매매 프로그램 (Paper Trading) |
| 성격 | 학부 졸업프로젝트 (3인 팀) |
| 핵심 가치 | 상용 코인거래소 UI/UX를 기반으로, ① 사용자가 파라미터로 전략을 설정하면 자동으로 매매를 실행하는 **자동매매**, ② 과거 데이터로 전략을 검증하는 **백테스팅** 기능 제공 |
| 범위 | 실거래 없음 (Paper Trading). 실 Upbit 계정 연동 없이 공개 시세 API만 사용 |

이 문서는 프로젝트의 뼈대(기술스택·아키텍처·데이터모델·공통 원칙·구현 순서)만 담는다. 화면별 상세 설계는 `features/*.md`에서 기능 단위로 관리한다.

---

## 2. 기술 스택

| 영역 | 선택 |
|---|---|
| Frontend | React + TypeScript |
| Backend | Python (FastAPI) |
| DB | PostgreSQL |
| 실시간 통신 | WebSocket — Upbit 공개 시세 API를 백엔드가 구독 → 프론트엔드로 브로드캐스트 |
| 자동매매 상시 실행 | 백엔드 상주 워커(스케줄러 기반, 예: APScheduler). 팀 판단에 따라 추후 Celery+Redis로 확장 가능 |
| 인증 | JWT (Access Token) |
| 수치 계산 | pandas/numpy — 지표 계산(RSI/MACD/MA/볼린저밴드) 및 백테스팅 시뮬레이션에 사용 |

> 상태관리 라이브러리(React Query, Zustand 등) 등 세부 프론트 구성은 인증 기능 구현 시작 시 함께 정한다 (TBD).

## 3. 시스템 아키텍처 개요

```
Upbit 공개 시세 WebSocket
        │
        ▼  백엔드가 기동 시 coins(is_active=true, KRW 마켓) 전체를 상시 구독
   FastAPI Backend
   ├─ 시세 캐시(메모리, 클라이언트 접속과 무관하게 항상 갱신)
   │     ├─ 체결 엔진(matcher) — 캐시 갱신마다 pending 지정가 주문 매칭·체결 (09-execution-engine)
   │     ├─ 자동매매 워커 — 손절·익절 현재가 비교
   │     └─ /ws/prices — 접속 클라이언트가 요청한 심볼만 필터링해 브로드캐스트 (화면 표시용)
   ├─ 전략 엔진 (공용 모듈: 지표 계산 + 신호 판단, runner.py)
   │     ├─ 백테스팅 배치 잡 (과거 데이터 replay)
   │     └─ 자동매매 워커 (실시간 데이터, 서버 상시 실행, 10초 tick)
   │            └─ 주문 실행기 (수동매매와 로직 공유) → orders 테이블 반영 → 체결 엔진 경유
   └─ PostgreSQL (사용자/잔고/주문/전략슬롯/백테스트결과/알림)
```

**핵심 설계 결정**: 자동매매 워커와 백테스팅 배치 잡은 같은 "전략 엔진" 모듈을 사용한다. 백테스팅에서 먼저 지표·신호 로직을 검증하고, 검증된 엔진을 자동매매 워커(실시간 인프라)에 그대로 얹는다 (7장 로드맵 참조).

**시세 구독 정책**: 시세 캐시는 클라이언트 접속과 무관하게 항상 갱신된다. 프론트엔드 구독(`/ws/prices`)은 이 캐시의 소비자일 뿐 백엔드의 Upbit 구독 대상을 결정하지 않는다 — 그렇지 않으면 아무도 접속하지 않은 시간대에 체결 엔진과 자동매매 손절·익절이 멈춰 원칙 1(서버 상시 실행)을 위반한다. 구독 심볼 집합은 `coins` 동기화 잡(로드맵 0번)이 마켓 목록을 갱신할 때 함께 재조정한다. 호가(orderbook)는 예외로, 데이터량이 커서 전체 구독하지 않고 사용자가 현재 보고 있는 심볼만 온디맨드로 구독한다 (`features/03-manual-trading.md`).

**체결 엔진**: 수동매매(03)의 지정가 주문과 자동매매(07)가 낸 주문(항상 시장가)은 모두 하나의 체결 엔진을 거쳐 `orders.status`가 확정된다. 상세 절차는 [features/09-execution-engine.md](features/09-execution-engine.md).

## 5. 데이터 모델 개요

**스키마의 단일 기준은 [01-erd.md](01-erd.md)다.** ERD·컬럼 타입·제약·인덱스·삭제 정책은 모두 그 문서에서 확정하며, 여기서는 엔티티 목록만 가볍게 요약한다. 기능 문서의 "데이터 모델" 절과 ERD가 어긋나면 ERD가 우선이다.

| 엔티티 | 설명 |
|---|---|
| `users` / `balances` | 계정 및 원화 잔고 (가입 시 시드머니 지급) |
| `coins` | 코인 마스터 (심볼·마켓코드) — 타 테이블의 심볼 FK 무결성 확보 |
| `watchlists` | 대시보드 관심 코인 (최대 5개) |
| `orders` / `holdings` | 매수·매도 체결 및 보유 코인 현황. `orders.source`로 수동/자동 구분. `orders.status` 전이(`pending→filled/canceled`)는 [features/09-execution-engine.md](features/09-execution-engine.md)의 체결 엔진이 담당 |
| `deposits_withdrawals` | 가상 원화 입출금 내역 |
| `notification_settings` / `notifications` | 알림 설정 및 알림(미확인 배지) |
| `strategy_slots` | 자동매매 슬롯 — 코인당 활성 1개 제약, `state`로 진행 상태 영속화 |
| `candles` | OHLCV 캐시 — 백테스팅 및 차트 조회 공용 |
| `backtest_results` / `backtest_trades` | 백테스팅 결과 및 체결 상세 |

## 6. 공통 설계 원칙 (Cross-cutting)

모든 기능 문서에 공통 적용되는 규칙. 개별 기능 문서에서 다시 서술하지 않는다.

1. **자동매매는 서버 상시 프로세스로 동작**한다. 사용자의 브라우저 접속 여부와 무관하게 워커가 전략을 수행한다. 프론트엔드 WebSocket은 화면 표시 전용이며 전략 판단 경로와 분리되어 있다.
2. **Paper Trading 전용** — 실 Upbit 계정/API 키 연동 없음. 시세는 Upbit 공개 API로 조회한다.
3. **알림은 DB에 영속화**되고 GNB 알림 아이콘에 미확인 배지 카운트로 표시한다. 브라우저 푸시는 접속 중 즉시 알림용, 알림 센터는 재접속 시 누적 확인용이다.
4. **코인당 활성 자동매매 슬롯은 1개**로 제한한다. 해당 코인은 수동매매 화면에서 주문 입력이 잠긴다 (조회는 가능).
5. **전략 유형 → 지표 → 파라미터 3단계 구조**를 자동매매·백테스팅 양쪽에 동일하게 적용한다.
   - 전략 유형: 추세추종 / 역추세 / 그리드 / DCA(분할매수)
   - 지표(추세추종·역추세 선택 시): MA / RSI / MACD / 볼린저 밴드
   - 손절·익절은 전략 유형별로 의미가 다르다 (추세추종·역추세는 표준 손절/익절, 그리드는 "이탈 손절"만, DCA는 "목표 수익률 익절"만).
6. **다크 모드 기반** UI (배경 `#1E1E1C`, 포인트 컬러 `#1D9E75`), GNB 공통 고정, 비로그인 상태에서 보호된 메뉴 클릭 시 로그인 모달.
7. **체결 비용은 수동·자동 실거래에 수수료만 적용**(0.05%)하고 슬리피지는 적용하지 않는다. 슬리피지는 실시세로 체결되지 않는 백테스팅에서만 존재하는 비용 항목이며, 이 비대칭은 의도된 설계다 (계산식은 [01-erd.md](01-erd.md) 3.2절). "백테스트 수익률이 실매매보다 다소 보수적으로 나올 수 있다"는 전제를 사용자에게 노출할 필요는 없으나, 개발 시 이 차이를 버그로 오인하지 않도록 유의한다.

## 7. 구현 로드맵

의존성 순서에 따라 아래 순으로 설계→구현을 반복한다. 완료 시 체크 표시.

- [ ] **0. 부트스트랩** — DB 마이그레이션 + `coins` 마스터 동기화 잡(앱 기동 시 1회 + 매일 1회, Upbit `/v1/market/all` KRW 마켓 폴링). 이후 모든 기능이 `coins.symbol` FK에 의존하므로 반드시 1번보다 먼저 완료
- [ ] **1. 인증** — 회원가입/로그인/JWT 인증 + 가입 시 초기 시드머니 자동 지급
- [ ] **2. 대시보드** — 화면 셸 우선 구현, 자동매매 상태 카드는 7번 완료 후 연결
- [ ] **3. 수동 매매** — `01-erd.md`의 잔고/보유코인/거래내역 모델을 실제로 구현, 이후 모든 기능의 기반이 됨. **체결 엔진**([features/09-execution-engine.md](features/09-execution-engine.md))을 이 단계에서 함께 구현 — 02에서 만든 시세 스트림 위에 훅을 얹는 형태이며, 07의 상시 워커와는 별개 컴포넌트
- [ ] **4. 공통 설정** — 계정 설정 + 알림 설정
- [ ] **5. 입출금** — 3번에서 확정된 잔고 모델 위에 충전/차감만 추가
- [ ] **6. 백테스팅** — 전략 엔진(지표 계산 + 신호 판단)을 정적 데이터로 먼저 검증
- [ ] **7. 자동매매** — 6번에서 검증된 엔진을 실시간 인프라(서버 상시 워커)에 연결
- [ ] **8. 포트폴리오** — 수동·자동 거래내역이 모두 갖춰진 뒤 마지막에 구현

## 8. 문서 관리 규칙

- `docs/features/NN-기능명.md` 형식으로 기능 하나당 파일 하나.
- 각 기능 문서는 상단에 상태 표기: `설계중 / 설계완료 / 구현중 / 완료`.
- **스키마 변경은 항상 `01-erd.md`를 먼저 고친다.** 구현 중 스키마를 바꿔야 하는 상황이 생기면 기능 문서나 코드부터 고치지 말고 ERD를 먼저 갱신한 뒤 관련 기능 문서를 따라 맞춘다.
- 구현 중 이 개요 문서(공통 원칙)와 충돌하는 결정이 생기면, 기능 문서만 고치지 말고 이 문서도 함께 갱신한다.
- 화면정의서/스토리보드 원본(.docx)은 삭제 완료 — `docs/` 구조가 유일한 기준 문서다.
- 코드 작성 시 명명·주석·프로젝트 구조·커밋 메시지 규칙은 [02-coding-conventions.md](02-coding-conventions.md)를 따른다.
