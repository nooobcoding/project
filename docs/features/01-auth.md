# 01. 인증 (로그인 / 회원가입)

**상태**: 설계완료 · 구현 전
**화면 ID**: SCR-01
**의존성**: 없음 (최초 구현 기능)
**연관 문서**: [00-overview.md](../00-overview.md) 6장(공통 원칙), 7장(로드맵 1번)

---

## 1. 목적

이메일·비밀번호 기반 계정 생성 및 JWT 인증. 가입 완료 시 자동 로그인 후 대시보드로 이동하며, **가입과 동시에 모의투자용 초기 시드머니를 지급**해 이후 수동매매(03) 구현 시 잔고 걱정 없이 바로 매매 로직을 붙일 수 있게 한다.

---

## 2. 화면 구성

레이아웃: 로그인(`/login`)과 회원가입(`/register`)을 별도 화면으로 분리한다. 각 화면은 폼 위에 상표("Gazua") + 단일 폼 패널로 구성되며, 하단 링크로 서로 이동한다.

### 2-A. 로그인 폼

| 컴포넌트 | 유형 | 동작 |
|---|---|---|
| 이메일 입력 | Input (text) | 이메일 형식 유효성 검사, 자동완성 허용 |
| 비밀번호 입력 | Input (password) | 마스킹, 표시/숨김 토글 |
| 로그인 유지 체크박스 | Checkbox | 기본 미체크. 체크 시 `localStorage`, 미체크 시 `sessionStorage`에 토큰 저장 |
| 로그인 버튼 | Button (Primary, 녹색) | 검증 후 JWT 발급, 로딩 상태 표시 |
| 회원가입 링크 | Hyperlink | `/register`로 이동 |

### 2-B. 회원가입 폼

| 컴포넌트 | 유형 | 동작 |
|---|---|---|
| 이메일 입력 | Input (text) | 형식 검사 + blur 시 중복 이메일 서버 검증 |
| 비밀번호 입력 | Input (password) | 8자 이상, 영문+숫자 포함, 실시간 조건 검사 |
| 비밀번호 확인 | Input (password) | 일치 여부 실시간 비교, 불일치 시 오류 배지 |
| 계정 생성 버튼 | Button (Primary, 녹색) | 전체 유효성 통과 시 활성화. 클릭 시 계정 생성 → **초기 시드머니 지급** → 자동 로그인 |
| 로그인 링크 | Hyperlink | `/login`으로 이동 |

## 3. 인터랙션 / 이벤트

| 위치 | 이벤트 | 처리 | 결과 |
|---|---|---|---|
| 로그인 버튼 | Click | `POST /api/auth/login` | 성공: 대시보드 리다이렉트 / 실패: 오류 메시지 |
| 로그인 유지 체크박스 | Check/Uncheck | 저장 위치 결정 | 브라우저 재시작 후 유지 여부 결정 |
| 이메일 입력 (회원가입) | Blur | 중복 여부 서버 검증 | 중복 시 "이미 사용 중인 이메일입니다" |
| 계정 생성 버튼 | Click | `POST /api/auth/register` → 계정 생성 → 잔고 초기화 → JWT 발급 | 성공: 대시보드 이동 / 실패: 서버 오류 메시지 |

## 4. 오류 처리

| 상황 | 메시지 | 처리 |
|---|---|---|
| 이메일·비밀번호 불일치 | 이메일 또는 비밀번호가 올바르지 않습니다. | 입력 초기화 없이 표시, 비밀번호 필드 포커스 |
| 이메일 형식 오류 | 올바른 이메일 형식을 입력해주세요. | 필드 테두리 빨간색 |
| 비밀번호 조건 미충족 | 비밀번호는 8자 이상, 영문과 숫자를 포함해야 합니다. | 인라인 오류 메시지 |
| 중복 이메일 | 이미 사용 중인 이메일입니다. | 이메일 필드 포커스 유지 |
| 서버 통신 오류 | 서버와 연결할 수 없습니다. 잠시 후 다시 시도해주세요. | 버튼 로딩 해제, 토스트 |

---

## 5. 초기 시드머니 지급 (신규 로직)

- 회원가입 성공 시 `balances` 레코드를 함께 생성하고 초기 원화 잔고를 지급한다.
- 기본 시드머니: **10,000,000원** (백테스팅 초기 투자금 기본값과 동일하게 맞춰 일관성 유지).
- 이 값은 상수로 관리하며, 추후 "모의투자 초기화"(포트폴리오 FR-P05) 시에도 동일 값으로 리셋한다.

## 6. 데이터 모델 (초안)

```
users
  id (PK)
  email (unique)
  password_hash
  created_at

balances
  user_id (PK, FK → users.id)
  krw_balance        -- 가입 시 10,000,000으로 초기화
  updated_at
```

## 7. API 엔드포인트 (초안)

| Method | Path | 설명 |
|---|---|---|
| POST | `/api/auth/register` | 계정 생성 + `balances` 초기화 + 토큰 발급 |
| POST | `/api/auth/login` | 로그인 + 토큰 발급 |
| POST | `/api/auth/logout` | 서버는 JWT를 무상태(stateless)로 검증하므로 폐기할 서버 측 상태가 없다. 이 엔드포인트는 감사 로그용이며, 실제 로그아웃 처리는 클라이언트가 `localStorage`/`sessionStorage`의 토큰을 삭제하는 것으로 완료된다 |
| GET | `/api/auth/check-email?email=` | (신규) 회원가입 이메일 입력 blur 시 중복 여부 검증. `{ "available": boolean }` 반환 |

## 8. 보안 참고 (미반영 — 추후 검토)

JWT를 `localStorage`에 저장하는 방식은 XSS에 취약한 알려진 패턴이다. 정식 서비스라면 Refresh Token은 HttpOnly 쿠키, Access Token은 메모리 보관이 더 안전하지만, 학부 졸프 범위·일정상 v1 구현은 원안(localStorage/sessionStorage)대로 진행한다. 시간이 남으면 재검토.

**Access Token 만료**: 24시간으로 고정한다 (Refresh Token 없음 — 만료 시 재로그인). "로그인 유지" 체크박스는 저장 위치(localStorage/sessionStorage)만 결정할 뿐 만료 시간 자체에는 영향을 주지 않는다.
