# 확장판 04 — Upbit 호출 일원화 + 백테스트 동시 실행 상한

**상태**: 설계 초안
**원본 대비**: [`docs/features/06-backtesting.md`](../docs/features/06-backtesting.md) 4장(타임아웃)에 동시 실행 상한을 더한다. **2장 전략 규칙, 2.6 엔진 구조, 2.7 비대칭, 3장 성과지표, 5장 데이터 모델, 6장 API 계약은 무수정으로 유효**하다.

> **이 문서는 한 번 축소됐다.** 초안은 `backtest_jobs` 테이블 + `SKIP LOCKED` 큐 + `job-worker` 역할을 담고 있었으나, 목표를 "프로세스를 늘릴 수 있게 만드는 것"으로 한정하면서 잡 큐를 통째로 뺐다. 근거는 2장. **3장(Upbit 호출 일원화)은 임계 경로에 그대로 남아 있으므로 이 문서를 통째로 건너뛰면 안 된다.**

---

## 1. 무엇이 문제였나

### 1.1 백테스트가 API 프로세스의 CPU를 점유한다

[`services/backtest.py`](../backend/app/services/backtest.py)는 요청마다 `ThreadPoolExecutor(max_workers=1)`을 만들고 `future.result(timeout=60)`으로 기다린다. **전역 동시 실행 상한이 없다.**

캐시가 찬 뒤의 백테스트는 CPU-bound다(1분봉 7일 계산 약 13초). Python 스레드라 GIL을 같은 프로세스의 다른 모든 것과 나눠 쓴다 — 현재 구조에서는 그 "다른 모든 것"에 자동매매 워커 tick과 모든 HTTP 요청이 포함된다.

### 1.2 Upbit REST 호출에 중앙 상한이 없다

[`services/candles.py`](../backend/app/services/candles.py)가 모듈 단위 `httpx.Client`를 재사용해 연결은 아끼지만, **호출량 자체를 통제하는 주체가 없다.** 1분봉 7일 백테스트 한 번이 51회 호출이고, rate limit은 IP 단위로 공유되므로 동시 사용자 몇 명이면 429가 나기 시작한다. 그 여파를 워커의 캔들 조회가 함께 맞는다.

---

## 2. 백테스트 — 세마포어로 끝낸다

### 2.1 절반은 프로세스 분리가 공짜로 해결한다

1.1절의 피해자는 둘이다. **워커 tick**과 **HTTP 요청**. 이 중 앞의 것은 별도 대응이 필요 없다.

[07-roadmap](07-roadmap.md) 4단계에서 시세 캐시가 Redis로 나가면 워커를 `api`와 다른 프로세스로 띄울 수 있게 되고([00-architecture](00-architecture.md) 2.1절), **그 순간부터 백테스트는 워커와 GIL을 공유하지 않는다.** "누가 무거운 백테스트를 돌리면 남의 손절이 밀린다"는 문제는 여기서 사라진다.

> 반대로 말하면 **4단계 전에는 워커를 분리할 수 없다.** 시세 캐시가 프로세스 메모리에 있어서 `market-data` 없는 프로세스의 워커는 가격을 못 읽기 때문이다 ([00-architecture](00-architecture.md) 1장 결합점 ②). 백테스트 격리를 서두를 이유가 없는 것도 이 때문이다.

### 2.2 남는 절반 — 전역 동시 실행 상한

프로세스를 분리해도 백테스트는 여전히 `api` 프로세스의 CPU를 먹고, 상한이 없다는 사실도 그대로다. 열 명이 동시에 실행 버튼을 누르면 스레드 열 개가 GIL을 두고 싸워서 **그 프로세스의 HTTP 응답이 통째로 밀린다.**

이건 흔한 상황이 아니라 **가장 흔한 상황**이다. 발표·시연처럼 사람이 몰리는 순간이 정확히 그렇다.

**해법은 모듈 단위 세마포어 하나다.**

```python
# services/backtest.py
_RUN_SLOTS = threading.Semaphore(BACKTEST_MAX_CONCURRENCY)   # 초안 2
```

- 실행 전에 획득하고 끝나면 반납한다. 못 잡으면 대기한다.
- 상한값은 호스트 코어 수를 넘지 않게 잡는다 (초안 2).
- **대기 시간도 60초 타임아웃 안에 포함**시킨다 — 대기하다 타임아웃되면 [`docs/features/06-backtesting.md`](../docs/features/06-backtesting.md) 4장의 기존 "처리 시간이 초과되었습니다" 문구가 그대로 나간다.

### 2.3 왜 잡 큐를 두지 않는가

`backtest_jobs` 테이블 + `SKIP LOCKED` 큐 + `job-worker` 프로세스로 가면 더 튼튼해지는 건 맞다. 그런데 그 대가가 이 프로젝트에는 맞지 않는다.

| 잡 큐가 추가로 요구하는 것 | 세마포어 |
|---|---|
| 신규 테이블 1개 + 마이그레이션 | 없음 |
| 신규 프로세스 역할 1종 (`job-worker`) | 없음 |
| **API 계약 변경** — `POST /api/backtest/jobs` → 202 + `job_id`, 진행 조회 API 신설 | 없음 |
| **프론트엔드 폴링 구현** | 없음 |
| 좀비 잡 회수 (`lease_until`), 재시도 상한, 멱등성 보장 | 없음 |
| 커넥션 예산 +6 ([00-architecture](00-architecture.md) 3.5절) | 없음 |

결정적인 건 세 번째 줄이다. **잡 큐는 이 확장판에서 프론트엔드를 건드리는 유일한 항목이었다.** 그게 빠지면서 [01-carryover-map](01-carryover-map.md) 4장의 "프론트엔드 거의 무수정"이 "관리자 화면 추가만"으로 깨끗해지고, [07-roadmap](07-roadmap.md)에서 **프론트·백을 함께 되돌려야 하는 유일한 단계가 사라진다.**

얻는 것과 견줘보면 — 잡 큐가 세마포어보다 나은 점은 (a) 백테스트가 배포·재시작을 견디고, (b) 사용자가 대기 중 다른 화면을 볼 수 있다는 것이다. 둘 다 **"프로세스를 늘릴 수 있게 만든다"는 목표와 무관하다.**

### 2.4 나중에 다시 꺼낼 조건

아래 중 하나라도 해당되면 잡 큐를 다시 검토한다.

- 백테스트 대기가 일상적으로 60초 타임아웃에 걸린다 (세마포어 상한을 올려도 해결 안 됨)
- 백테스트 외에 비동기로 돌려야 할 잡이 생긴다
- 백테스트가 배포 때마다 끊기는 게 실제로 문제가 된다

그때는 `enqueue_backtest()` / `claim_next_job()` 인터페이스만 맞추면 호출부는 안 바뀐다. **지금 세마포어를 넣어도 그 길이 막히지 않는다** — 세마포어는 `services/backtest.py` 안에서 끝나는 변경이다.

## 3. Upbit REST 호출 일원화

**여기서부터는 임계 경로다.** [07-roadmap](07-roadmap.md) 6단계이며, 7단계(워커 샤딩)가 의미를 가지려면 반드시 선행돼야 한다.

### 3.1 `scheduler` 역할이 유일한 호출 주체가 된다

| 호출 | 현재 주체 | 확장판 주체 |
|---|---|---|
| `/v1/market/all` (coins 동기화) | API 프로세스의 APScheduler | `scheduler` |
| 최신 캔들 (`get_candles` 캐시 미스) | 요청한 아무 경로 (워커 포함) | `scheduler`가 미리 채움 ([03](03-worker-orchestration.md) 5.1절) |
| 과거 캔들 기간 조회 (`get_candles_in_range`) | 백테스트 실행 스레드 | `api`의 백테스트 스레드 — **단, 토큰 버킷을 통과해야 함** (3.2절) |

**워커는 Upbit를 전혀 부르지 않게 된다. 이것이 tick 예산을 지키는 핵심이다.**

[03](03-worker-orchestration.md) 1장의 계산 — 서로 다른 코인 50종에 1분봉을 걸면 매 분 정각에 50회 × 0.27초 ≈ 13.5초 — 가 10초 예산을 넘기는 문제가 여기서 해소된다.

### 3.2 토큰 버킷

Redis 키 `ratelimit:upbit:rest`에 토큰 버킷을 둔다. REST를 부르기 전에 토큰을 소비하고, 없으면 대기한다.

- **버킷 용량과 리필 속도는 Upbit 공개 제한보다 보수적으로 잡는다.** 실측으로 조정하되, 429를 받으면 자동으로 리필 속도를 낮추는 백오프를 둔다.
- **우선순위**: `scheduler`의 캔들 미리 채우기가 백테스트보다 **높다.** 워커의 신호 평가가 거기에 걸려 있기 때문이다. 백테스트는 좀 늦어도 되지만 자동매매가 멈추면 안 된다.
- 구현은 별도 버킷 두 개(`...:high`, `...:low`)로 나누고 총량을 나눠 갖는 방식이 단순하다.

> 잡 큐를 빼면서 저우선 소비자가 `job-worker`에서 `api`(백테스트 스레드)로 바뀌었을 뿐, **우선순위 규칙 자체는 그대로다.** 오히려 소비 주체가 세마포어로 이미 제한돼 있어 저우선 쪽 압력이 예측 가능해졌다.

### 3.3 캔들 미리 채우기

`scheduler`가 주기적으로:

```sql
SELECT DISTINCT coin_symbol, (params->>'interval') AS interval
FROM strategy_slots WHERE is_active;
```

로 대상 조합을 뽑아, 각 조합의 최신 확정봉이 DB에 있는지 확인하고 없으면 채운다. 봉 주기별로 채우는 시점을 다르게 잡는다 (1분봉은 매 분 경계 직후, 일봉은 하루 한 번).

**이 잡이 밀리면 워커가 평가를 건너뛴다**([03](03-worker-orchestration.md) 5.1절)는 점이 중요하다. `scheduler`의 채우기 소요 시간도 관측 대상이다 ([06](06-observability.md)).

## 4. 검증 방법

1. **회귀**: 백테스트 도메인 로직은 안 건드리므로 `tests/test_metrics.py`·`test_backtest_service_db.py` 등 기존 테스트 전부 통과
2. **동시 실행 상한**: 백테스트 10개를 동시에 요청해 실제 동시 실행이 `BACKTEST_MAX_CONCURRENCY`를 넘지 않는지, 대기분이 타임아웃 문구를 제대로 받는지
3. **GIL 격리**: 백테스트를 여러 개 돌리는 동안 워커 `last_duration_ms`가 늘지 않는지 — **4단계(워커 프로세스 분리) 전후로 비교하면 2.1절 주장이 숫자로 확인된다** ([06](06-observability.md) 지표)
4. **워커가 Upbit를 안 부르는지**: 워커 프로세스의 아웃바운드 HTTP를 차단해도 tick이 정상 동작하는지 (캔들이 DB에 있는 한)
5. **토큰 버킷 우선순위**: 백테스트를 여러 개 돌리는 동안 `scheduler`의 캔들 채우기가 굶지 않는지
6. **429 백오프**: 리필 속도를 인위적으로 높여 429를 유발하고, 자동으로 낮아지는지
