# 확장판 08 — 실측 처리 한계

**상태**: 측정 완료 (2026-10-05)
**목적**: [07-roadmap](07-roadmap.md) "그래서 몇 명까지인가"의 추정치를 실측치로 바꾼다. 확장판의 출발점은 "프로세스를 나눠 더 많은 사용자를 받는다"였는데([00](00-architecture.md) 1장), 나눌 수 있게 만든 뒤 **실제로 늘어나는지**는 잰 적이 없었다.

## 0. 요약

| | 원래 (단일 프로세스, 측정 전 코드) | 지금 (단일 프로세스) | 지금 (여러 프로세스) |
|---|---|---|---|
| API 처리량 | **동시 25명에서 붕괴** (p95 30초, 50명에서 실패 51%) | 약 **300 RPS**, 200명까지 실패 0% | 약 **915 RPS** (api 4프로세스), 400명까지 실패 0% |
| 자동매매 슬롯 (1분봉 전부, 10초 예산) | 약 **1,300개** | 약 **3,500개** | 약 **10,000개** (워커 4개) |

측정하면서 **버그 2개와 병목 3개**를 찾아 고쳤다. 원래 구성의 한계는 CPU나 DB가 아니라 버그였다 (2장).

**환경**: Windows 11 + Docker Desktop(WSL2), Docker에 CPU 12개 / 메모리 8GB, 모든 프로세스·PostgreSQL·Redis가 한 호스트. 이 호스트의 디스크 동기화(fdatasync)는 **1회 2.8ms**로 서버용 NVMe(대개 0.05~0.5ms)보다 수 배 느리다 — 4장의 슬롯 한계는 이 값에 직접 묶여 있다.

도구와 재현 방법: [`backend/scripts/load/`](../../backend/scripts/load/) (5장).

## 1. 측정 전에 고친 것 — 프로세스를 늘려도 안 늘던 이유

`ShardLocks`가 잡히는 샤드를 **전부** 가져가서, 먼저 뜬 워커가 16개를 다 쥐고 나중 워커는 페일오버 대기만 했다. **워커를 몇 개 띄우든 일하는 건 하나**였다. 공정 몫(참여자 수로 나눈 몫)으로 바꿨다 — [03 2.1절](03-worker-orchestration.md). 실제 컨테이너로 `[0 1 2 3]` → `[0 1]`/`[2 3]` → 하나를 SIGKILL하면 9초 뒤 `[0 1 2 3]`.

여러 프로세스 실행 구성도 저장소에 없었다 — `docker-compose.scale.yml`을 추가했다 (5장).

## 2. API — 원래 구성은 버그 때문에 25명에서 무너졌다

k6로 VU(가상 사용자)마다 [대시보드 요약·보유 자산·미체결 주문·전략 슬롯]을 동시에 4건 요청하고, 열 번에 한 번 소액 시장가 매수를 섞었다. 반복 사이 0.2초 쉰다 — **사람보다 훨씬 공격적인 부하**다 (6장 해석 참고).

### 2.1 원래 단일 프로세스

| VU | RPS | p95 | 실패율 |
|---|---|---|---|
| 10 | 168 | 81ms | 0% |
| 25 | **15** | **30.1초** | 7% |
| 50 | **4** | **60초** | 51% |

p95가 정확히 30초 = SQLAlchemy 풀 대기 한도. 그런데 CPU도 DB도 한가했다.

**원인 (버그 1)**: 요청 하나가 스레드를 두 번 탄다. 인증 의존성이 스레드에서 커넥션을 잡고 **스레드만 반납**하며(세션은 요청 끝까지 산다 — `idle in transaction`으로 쌓여 있었다), 엔드포인트 본문이 다시 스레드를 기다린다. 처리 중 요청이 커넥션 수(15)를 넘으면 스레드 40개가 전부 커넥션을 기다리고, 커넥션은 전부 스레드를 기다리는 요청이 쥔다. 30초 뒤 타임아웃으로 풀릴 때까지 서로를 기다린다.

풀을 키워서는 안 고쳐진다 — 처리 중 요청 수에 상한이 없어 확률만 준다. **처리 중 요청을 커넥션 수 이하로 묶는 입장 제한**([`app/http_admission.py`](../../backend/app/http_admission.py))으로 고쳤다. 넘치는 요청은 스레드도 커넥션도 쥐지 않고 이벤트 루프에서 기다린다.

**버그 2**: 호가 웹소켓이 `Depends(get_session)`으로 받은 세션을 탭이 열려 있는 **내내** 쥐었다. 호가창 15개면 풀 전체가 묶인다. 조회만 짧은 세션으로 하도록 고쳤다.

### 2.2 고친 뒤

| VU | 단일 프로세스 RPS / p95 | api 4프로세스 RPS / p95 |
|---|---|---|
| 25 | 320 / 195ms | 421 / 77ms |
| 50 | 302 / 570ms | 735 / 122ms |
| 100 | 302 / 1.3초 | 867 / 377ms |
| 200 | 301 / 2.7초 | 917 / 919ms |
| 400 | — | 916 / 1.8초 |

실패율·풀 타임아웃 **전 구간 0**. 단일 프로세스는 약 300 RPS(파이썬 프로세스 하나 = 코어 하나)에서 포화하고, 그 뒤로는 실패 없이 지연만 는다. **api 4프로세스는 약 3배.** 4배가 아닌 건 같은 호스트에서 PostgreSQL·워커와 CPU를 나눠 쓰기 때문이다.

## 3. 워커 — 슬롯마다 매 tick 같은 캔들을 읽고 있었다

유저마다 활성 슬롯 1개, 실제 KRW 마켓 24개 코인, **전부 1분봉**(가장 무거운 경우 — 매분 모든 슬롯이 동시에 새 봉을 평가한다), 전략 8종을 섞었다. 판정 기준은 **가장 느린 tick(=봉 경계 tick)이 10초 예산 안인가**다.

### 3.1 가장 느린 tick (초)

| 슬롯 | 원래 코드 워커 1 | 최적화 후 워커 1 | 워커 2 | 워커 4 |
|---|---|---|---|---|
| 1,000 | 7.5 | — | — | — |
| 2,000 | **17.2** ✗ | 5.6 | 3.1 | 3.5 |
| 5,000 | — | **15.3** ✗ | 8.1 | 7.4 |
| 10,000 | — | **39.2** ✗ | **20.6** ✗ | 9.7 |
| 20,000 | — | **130 초과** ✗ | **39.5** ✗ | **15.2** ✗ |

(✗ 예산 초과. 최적화 후 값은 두 차례 측정 중 새로 시드한 슬롯의 첫 평가 몰림을 뺀 쪽이다 — 3.4절)

### 3.2 고친 병목

1. **캔들 반복 조회** — 슬롯마다 매 tick 확정봉 ~200개를 DB에서 읽었다. 그 직후 `claim_candle`이 "새 봉 없음"으로 대부분 돌려보내는데도. 슬롯 처리 6.3ms 중 **6.1ms(97%)** 가 이것이었다. 슬롯이 수천 개여도 (코인, 간격) 조합은 수십 개다 → tick 안에서 조합마다 한 번만 읽는다.
2. **헛된 선점 트랜잭션** — 새 봉이 없는 tick에도 슬롯마다 `claim_candle`의 UPDATE·커밋을 쳤다. 스냅샷이 "이미 평가함"이면 건너뛴다(평가를 *허락*하는 판정은 여전히 `claim_candle`만 한다).

두 개로 **봉 경계가 아닌 tick의 비용이 거의 사라졌다** (워커 4 × 슬롯 1만에서 중앙값 tick 5.0초 → 1.7초).

### 3.3 남은 한계 — 디스크 동기화

봉 경계 tick에서는 슬롯마다 `claim_candle` 커밋 1회가 남는다. 이건 **중복 주문을 막는 안전장치라 줄이지 않았다** — 커밋을 비동기로 바꾸면 장애 직후 같은 봉으로 다시 주문할 수 있다.

이 호스트에서 커밋 1회 = fdatasync 2.8ms이고, 봉 경계에서 슬롯당 비용이 2.8~3.9ms로 거의 같다. 봉 경계 tick 동안 워커 CPU는 40~50%, PostgreSQL 대기는 `IO:WALSync`·`LWLock:WALWrite`였다 — **계산이 아니라 WAL 동기화를 기다린다.** 워커를 늘려도 하나뿐인 WAL을 같이 쓰므로 선형으로 늘지 않는다(2→4에서 그룹 커밋 덕에 조금 준다).

### 3.4 측정 주의

- **새 슬롯이 한꺼번에 생기면** 첫 봉 경계에서 전부 처음 평가되고, 진입 신호가 실제 시장가 주문으로 쏟아진다. 같은 조건에서 15.3초 → 29.8초로 튄 측정이 이것이었다. 정상 상태 한계와 구분해야 한다.
- 1분봉은 최악의 경우다. 1시간·1일봉 슬롯은 봉 경계가 드물어 거의 공짜다.

## 4. 커넥션

| 역할 | 구성 (scale) | 실측 |
|---|---|---|
| api | 4프로세스 × (10 + 10) | 입장 제한이 프로세스당 처리 중 요청을 20으로 묶는다 → 상한 80 |
| worker | 4 × (3 + 5) + 샤드 전용 1 | heartbeat `db_connections` 피크 **1** (tick이 단일 스레드) |
| matcher | 2 × (3 + 5) + 샤드 전용 1 | 피크 1 |
| market-data, scheduler | 각 (3 + 5) + 리더 전용 1 | — |

전체 대기 상태 17개. `max_connections`는 300으로 올렸다 — scale 파일에만 두면 기본 파일로 `docker compose run`을 할 때(test_matrix.sh) postgres가 재생성돼 모든 커넥션이 끊겼다(실제로 일어났다). 그래서 기본 compose로 옮겼다.

[00-architecture 3.5절](00-architecture.md)의 초안 표는 api를 3프로세스 × 10으로 잡았는데, 입장 제한이 생긴 지금은 **api 풀 = api 동시 처리량**이다. 풀을 줄이면 처리량이 같이 준다.

## 5. 재현

```bash
# 여러 프로세스 구성
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --build \
    --scale worker=4 --scale matcher=2

# 워커: 워커 수 × 슬롯 수
bash backend/scripts/load/bench_worker.sh "1 2 4" "2000 5000 10000"
docker compose run --rm -T --no-deps backend python scripts/load/cleanup.py --run bench

# API: 지금 떠 있는 구성을 잰다 (단일과 비교하려면 구성을 바꿔 두 번)
bash backend/scripts/load/bench_api.sh "25 50 100 200"
docker compose run --rm -T --no-deps backend python scripts/load/cleanup.py --run api

# 원래 구성으로
docker compose -f docker-compose.yml -f docker-compose.scale.yml down && docker compose up -d
```

측정 데이터는 `load-<run>-N@example.com` 유저로 개발 DB에 들어간다. **측정이 끝나면 반드시 지운다** — 남겨 두면 모든 샤드에 슬롯이 생겨 "한가한 샤드"가 필요한 테스트 2개가 건너뛰어진다(실제로 그랬다).

## 6. 그래서 몇 명까지인가 (이 호스트 기준)

**API**: VU 하나는 약 0.2~0.5초마다 요청 4~5건을 보낸다 — 화면을 보는 사람(몇 초에 한 번)보다 10배 이상 공격적이다. 사람 한 명을 초당 0.5요청으로 잡으면:

- 원래 구성: 동시 요청이 15개를 넘는 순간 무너졌다 — **수십 명 수준**
- 지금 단일 프로세스: 300 RPS ≈ **동시 활동 사용자 약 600명**
- 지금 api 4프로세스: 915 RPS ≈ **약 1,800명**

**자동매매 (1분봉 기준)**: 단일 워커 약 3,500슬롯, 워커 4개 약 10,000슬롯. 1시간·1일봉이 섞이면 훨씬 많다.

**다음 한계는 디스크 동기화다.** 같은 코드라도 서버 NVMe(동기화 0.1ms대)에서는 봉 경계 tick 비용이 크게 준다. 코드로 더 가려면 봉 경계의 선점을 슬롯마다가 아니라 **(코인, 간격) 단위로 묶어 커밋 한 번에** 하는 방법이 있다 — 장애 시 의미(선점 후 평가 전에 죽으면 그 봉은 건너뜀)가 지금과 같아서 안전성을 잃지 않는다. 아직 하지 않았다.
