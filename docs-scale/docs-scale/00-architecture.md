## 1. 왜 바꾸는가 — 단일 프로세스 가정이 박힌 곳은 정확히 3군데다

현재 구조는 기능이 부족한 게 아니라 **프로세스를 하나밖에 못 띄운다**. `uvicorn --workers 2`를 하는 순간 자동매매 주문이 중복으로 나간다. 원인은 셋뿐이다.

### ① 스케줄러와 시세 스트림이 API 프로세스 안에 있다

[`backend/app/main.py`](../backend/app/main.py) `lifespan`이 `coin_sync` 잡, 자동매매 `run_tick` 잡, `price_stream` 태스크를 전부 기동한다. API 프로세스를 늘리면 이것들이 프로세스 수만큼 복제된다. `max_instances=1`은 **한 프로세스 안에서만** 유효하다.

### ② 시세 캐시가 프로세스 메모리 dict다

`services/price_stream.py`의 `_price_cache`를 읽는 곳이 **7개 모듈**이다 — `routers/prices.py`, `services/coins.py`, `services/dashboard.py`, `services/orders.py`, `services/portfolio.py`, `strategy_engine/worker.py`, 그리고 `services/matcher.py`(간접). 프로세스를 쪼개는 순간 시세를 구독하지 않는 프로세스의 워커는 **가격을 아예 못 읽는다**. 이것이 가장 깊은 결합점이다.

### ③ 체결 엔진이 시세 수신 루프 안에서 돈다

`price_stream._stream_once()`가 틱마다 `asyncio.to_thread(_run_matcher_safely, ...)`로 매칭을 호출한다. 시세 프로세스와 체결 프로세스가 물리적으로 같은 프로세스다.

> **뒤집어 말하면**: 이 셋 말고는 단일 프로세스를 가정한 코드가 없다. 잔고·보유수량·슬롯 상태의 정합성은 전부 PostgreSQL 행 잠금으로 잡혀 있어서, **프로세스가 몇 개든 그대로 맞다.** 이것이 이 확장이 처음부터 다시 만드는 일이 아닌 이유다.

## 2. 목표 토폴로지

```
                    ┌──────────────┐
   Upbit ticker WS  │ market-data  │  리더 1개 (advisory lock)
   ────────────────►│              │──► Redis  price:{symbol}      (최신 틱 캐시)
                    └──────────────┘        └─ pub/sub ticks:{symbol}
                                                     │
                        ┌────────────────────────────┼───────────────┐
                        ▼                            ▼               ▼
                 ┌────────────┐              ┌────────────┐   ┌────────────┐
                 │  matcher   │ 심볼 샤드 N  │   worker   │유저샤드N│  api   │ N (stateless)
                 │ 지정가 체결 │              │ 자동매매tick│   │ 스케줄러 없음│
                 └─────┬──────┘              └─────┬──────┘   └─────┬──────┘
                       │                           │                │
                       └───────────┬───────────────┴────────────────┘
                                   ▼
                          ┌─────────────────┐
                          │   PostgreSQL    │  ◄── 자금·주문·슬롯의 단일 진실원천
                          └─────────────────┘         (행 잠금 = 정합성 경계)
                                   ▲
                          ┌────────┴────────┐
                          │    scheduler    │ 리더 1개
                          │ coin-sync       │
                          │ candle-refresh  │
                          │ (Upbit REST     │
                          │  호출 일원화)    │
                          └─────────────────┘
```

### 프로세스 역할 5종

| 역할 | 개수 | 하는 일 | 상세 |
|---|---|---|---|
| `api` | N (stateless) | HTTP·WS 요청 처리만. 스케줄러·스트림 없음. 백테스트도 여기서 돈다(세마포어 상한) | [04](04-async-jobs.md) 2장 |
| `market-data` | **1** (리더 선출) | Upbit ticker WS 구독 → Redis 캐시 갱신 + pub/sub 발행 | [02](02-market-data.md) |
| `matcher` | N (**심볼** 샤드) | 틱 구독 → pending 지정가·예약가 처리 | [02](02-market-data.md) 4장 |
| `worker` | N (**유저** 샤드) | 자동매매 10초 tick | [03](03-worker-orchestration.md) |
| `scheduler` | **1** (리더 선출) | `coin_sync` + 캔들 미리 채우기. **Upbit REST 호출을 여기로 일원화** | [04](04-async-jobs.md) 3장 |

> **`job-worker` 역할은 두지 않는다.** 백테스트를 별도 프로세스의 잡 큐로 빼는 안을 검토했으나, 목표를 "프로세스를 늘릴 수 있게 만드는 것"으로 한정한 이상 임계 경로가 아니라고 판단해 뺐다. 근거와 대안은 [04](04-async-jobs.md) 2장.

### 2.1 역할은 논리적 분리, 배치는 설정으로 결정

**프로세스 6개를 항상 띄우라는 뜻이 아니다.** 로컬 개발에서 6개를 띄우면 개발이 안 된다. 역할을 환경변수로 켜고 끈다.

```bash
# 로컬 개발 — 지금과 완전히 동일한 단일 프로세스
PROCESS_ROLES=api,market-data,matcher,worker,scheduler

# 운영 — 역할별 분리
PROCESS_ROLES=api                      # × 3
PROCESS_ROLES=market-data,scheduler    # × 2 (리더 선출로 실제 활성은 각 1)
PROCESS_ROLES=matcher,worker           # × 4
```

이 규칙이 중요한 이유는 **[07-roadmap.md](07-roadmap.md)의 모든 단계를 되돌릴 수 있게 만들기 때문**이다. 어느 단계에서 문제가 생겨도 `PROCESS_ROLES`를 전부 켠 단일 프로세스로 되돌리면 현재 동작으로 복귀한다.

## 3. 전역 규칙 (모든 하위 문서에 공통 적용)

### 3.1 샤딩 키는 역할마다 다르다

**역할마다 샤딩 키가 다르다.** 하나로 통일하고 싶은 유혹이 있지만, 두 역할이 샤딩으로 얻으려는 것이 서로 다르다.

| 역할 | 샤딩 키 | 왜 이 키인가 |
|---|---|---|
| `matcher` | `coin_symbol` (`crc32(symbol) % SHARD_COUNT`) | 틱이 심볼 단위로 오고, **한 심볼 안에서의 체결 순서**를 보장해야 한다 |
| `worker` | `user_id` (`user_id % SHARD_COUNT`) | 슬롯 평가에는 심볼 순서가 필요 없다. 균등 분포가 훨씬 중요하다 |

**워커를 심볼로 샤딩하면 안 되는 이유**: 슬롯 분포는 절대 균등하지 않다. 사용자 상당수가 BTC에 슬롯을 걸면 그 슬롯이 전부 샤드 하나에 몰리고, **워커 프로세스를 아무리 늘려도 그 샤드를 처리하는 프로세스는 하나뿐이다.** 심볼 샤딩은 확장이 심볼 다양성에 종속되게 만든다.

반면 워커에는 심볼 친화성이 필요 없다. 같은 코인이라도 유저가 다르면 슬롯끼리 완전히 독립이고([`docs/00-overview.md`](../docs/00-overview.md) 6장 원칙 4 — 유저·코인당 활성 슬롯 1개), 캔들은 DB에서, 시세는 Redis에서 읽으므로 프로세스 안에 심볼 단위로 쌓아둘 상태가 없다.

`user_id % SHARD_COUNT`는 덤도 준다 — 애플리케이션과 SQL이 **같은 식을 그대로 쓸 수 있어서** `crc32` 구현이 양쪽에서 일치하는지 걱정할 필요가 없다 ([03](03-worker-orchestration.md) 2.1절).

### 3.1.1 샤딩은 처리량 분산이지 정합성 수단이 **아니다**

가장 착각하기 쉬운 지점이라 못을 박는다. **자금은 유저 단위**인데, 유저 A의 `balances` 행을 건드리는 주체는 워커만이 아니다. A의 슬롯이 전부 같은 워커 샤드에 모여도 — matcher(심볼 샤드)가 A의 지정가 주문을 체결하고, api 프로세스가 A의 수동 주문·입출금을 처리한다. **셋이 동시에 같은 행을 갱신한다.**

따라서:

> **[`docs/features/09-execution-engine.md`](../docs/features/09-execution-engine.md) 3.4절 "잠금 순서 규칙"은 확장판에서 폐기되지 않는다. 그대로 유효하고, 오히려 더 중요해진다.**

같은 프로세스 안의 스레드 두 개가 경합하던 것이 프로세스 두 개의 경합으로 바뀔 뿐이고, 방어 수단(`balances` 행 `FOR UPDATE` 선점)은 정확히 동일하다. PostgreSQL이 프로세스 경계를 모르기 때문에 그대로 동작한다.

**샤딩이 실제로 보장하는 것은 이것뿐이다**: matcher는 한 심볼 안에서의 처리 순서를, worker는 한 유저의 슬롯이 두 워커에서 동시에 평가되지 않음을 보장한다. 그 이상은 DB가 한다.

### 3.2 Redis에 두는 것과 두지 않는 것

| Redis에 둔다 | PostgreSQL에만 둔다 |
|---|---|
| 최신 시세 틱 (`price:{symbol}`) | 잔고·보유수량·주문 |
| 틱 팬아웃 (pub/sub) | 슬롯 `state` (포지션·그리드 라인·DCA 진행) |
| pending 주문 보유 심볼 집합 (조회 스킵용 힌트) | 관측 지표 (`worker_heartbeats`) |
| Upbit 호출 토큰 버킷 | 사용자·권한 |

**원칙: 잃어버려도 재구성 가능한 것만 Redis에 둔다.** Redis가 통째로 날아가도 시세는 다음 틱에 다시 차고, 심볼 집합은 DB에서 재계산되며, 토큰 버킷은 보수적으로 리셋된다. 자금은 단 한 바이트도 Redis에 두지 않는다.

**왜 Redis인가**: 초당 수백 틱을 PostgreSQL에 쓰면 WAL이 감당하지 못한다. `LISTEN/NOTIFY`는 (a) 페이로드 8000바이트 제한, (b) **커밋 시점에만 발행**되어 캐시 갱신 같은 비트랜잭션 이벤트에 맞지 않아 부적합하다.

### 3.3 리더 선출은 PostgreSQL advisory lock으로 한다

`market-data`와 `scheduler`는 정확히 1개만 활성이어야 한다. 별도 코디네이터(etcd·ZooKeeper·Redis lock)를 들이지 않고 **이미 있는 PostgreSQL**을 쓴다.

```sql
SELECT pg_try_advisory_lock(<namespace>, <role_id>);
```

- 락을 잡은 프로세스만 해당 역할을 수행하고, 못 잡은 프로세스는 대기하며 주기적으로 재시도한다.
- **세션이 끊기면 락이 자동 해제된다** — 프로세스가 죽거나 네트워크가 끊기면 페일오버가 공짜로 따라온다. 별도 하트비트 만료 로직이 필요 없다.
- 같은 메커니즘을 워커 샤드 점유에도 쓴다 ([03](03-worker-orchestration.md) 2장).

**주의**: advisory lock은 **세션 단위**다. SQLAlchemy 커넥션 풀이 커넥션을 재활용하면 락이 풀린다. 리더 역할은 풀에서 꺼낸 커넥션이 아니라 **전용 커넥션 하나를 붙잡고** 유지해야 한다. 이 함정을 [03](03-worker-orchestration.md) 2.2절에 다시 적어둔다.

### 3.4 조용한 실패를 금지한다

현재 구조의 가장 나쁜 성질은 tick 예산을 초과했을 때 APScheduler `coalesce`가 **로그 한 줄 없이** 실행을 건너뛴다는 것이다. 확장판에서는 다음을 강제한다.

- 모든 tick은 소요 시간을 기록한다.
- 예산(10초) 초과는 경고 로그 + 관측 지표로 남긴다.
- 워커가 캔들을 못 찾아 평가를 건너뛰면 그것도 기록한다 (지금은 아무 흔적이 없다).

상세는 [06-observability.md](06-observability.md).

### 3.5 커넥션 예산을 먼저 정하고 프로세스를 늘린다

프로세스를 늘리는 설계의 가장 조용한 실패 지점이다. **역할을 쪼갤수록 PostgreSQL 커넥션이 프로세스 수에 비례해 늘어나는데, 지금 코드에는 풀 설정이 아예 없다.**

[`backend/app/database.py`](../backend/app/database.py)의 `create_engine(settings.database_url)`은 SQLAlchemy 기본값을 쓴다 — `pool_size=5` + `max_overflow=10` = **프로세스당 최대 15개**. 2.1절의 운영 예시를 그대로 띄우면 프로세스 9개 × 15 = 135개에 리더·샤드 점유용 전용 커넥션이 더 붙는다. PostgreSQL 기본 `max_connections`는 **100**이다. 즉 이 문서가 예시로 든 배치는 기본 설정의 DB에 들어가지 않는다.

**전용 커넥션은 풀 바깥이라는 점을 반드시 함께 센다.** advisory lock은 세션 단위라 풀에서 꺼낸 커넥션으로 잡으면 안 되고([03](03-worker-orchestration.md) 2.2절), 그래서 리더·샤드 점유 커넥션은 `pool_size`에 포함되지 않는 순수 추가분이다.

#### 역할별 풀 크기 (초안)

| 역할 | 프로세스 | `pool_size` + `max_overflow` | 전용 | 소계 |
|---|---|---|---|---|
| `api` | 3 | 5 + 5 | — | 30 |
| `matcher,worker` | 4 | 3 + 2 | 2 (역할당 1) | 28 |
| `market-data,scheduler` | 2 | 2 + 2 | 2 (역할당 1) | 12 |
| | | | **합계** | **70** |

기본 `max_connections=100` 안에 여유를 두고 들어간다. 값 자체는 [06](06-observability.md)의 실측으로 조정하되, **규칙은 하나다 — 프로세스를 늘리기 전에 이 표를 먼저 갱신한다.**

#### PgBouncer는 두지 않는다

커넥션 풀러를 하나 더 세우는 대신 **풀 크기 설정으로 해결한다.** 이 규모에서 운영 대상을 늘릴 이유가 없고, 같은 이유로 [06](06-observability.md) 4장도 Prometheus를 거절했다. 역할별 풀 설정으로 예산이 안 맞는 시점이 오면 그때 재검토한다.

## 4. 무엇을 하지 않는가 (명시적 비목표)

과욕으로 프로젝트를 망치지 않기 위해 범위 밖을 먼저 못 박는다.

| 하지 않는 것 | 이유 |
|---|---|
| 자체 매칭 엔진(오더북) 구현 | Paper Trading이고 시세 원천은 Upbit다. 오더북을 만들면 그건 다른 프로젝트다 |
| 인메모리 원장 + 비동기 영속화 | 실제 거래소 방식이지만, 지금의 DB 행 잠금 설계를 통째로 버려야 한다. 얻는 처리량이 이 프로젝트에 필요 없다 |
| Kubernetes·오토스케일링·로드밸런서·TLS·시크릿 관리 | 프로세스 역할 분리까지가 목표다. **배포·오케스트레이션은 통째로 범위 밖**이며, 이 확장이 끝나도 여기가 다음 벽으로 남는다 ([07](07-roadmap.md) "완료 후에도 남는 한계") |
| 백테스트 잡 큐 (`job-worker` 역할) | 임계 경로가 아니다. 동시 실행 상한은 세마포어로 얻는다 ([04](04-async-jobs.md) 2장) |
| PgBouncer 등 커넥션 풀러 | 역할별 풀 크기 설정으로 해결한다 (3.5절) |
| 읽기 복제본·파티셔닝 | 단일 PostgreSQL 쓰기 노드를 전제로 한다 |
| 이벤트 소싱 / CQRS | 현재 스키마와 정합성 모델을 전부 갈아야 한다 |
| 실거래 연동 | [`docs/00-overview.md`](../docs/00-overview.md) 6장 원칙 2 유지 |

**이 확장판의 목표는 단 하나다**: 같은 기능·같은 정합성을 유지한 채 **프로세스를 늘릴 수 있게 만드는 것**.

여기서 얻는 것은 "늘어난 처리량"이 아니라 **"늘릴 수 있는 능력"**이다. 실제 처리량은 호스트를 늘리는 순간부터 생기고, 그건 위 표의 첫 줄에 따라 범위 밖이다. 한계가 코드에서 인프라로 옮겨가는 것 자체가 이 작업의 성과다.

## 5. 열린 질문 (착수 전에 정해야 함)

정직하게, 아직 답이 없는 것들이다.

1. **`SHARD_COUNT`를 몇으로 고정할 것인가.** 고정 상수여야 재해싱이 없다. 16이면 충분해 보이지만 근거는 없다 — [06](06-observability.md)의 관측을 먼저 붙여 실측한 뒤 정하는 것을 권한다. `matcher`와 `worker`가 샤딩 키는 다르지만(3.1절) **상수는 하나를 공유한다** — 노브를 둘로 늘릴 만큼 둘의 분포가 다르다는 근거가 아직 없다.
2. **market-data 페일오버 공백 동안의 stale 가격을 어떻게 다룰 것인가.** 틱에 타임스탬프를 넣고 N초 이상 오래된 가격을 거부하는 안을 [02](02-market-data.md) 3.3절에 적었지만, N을 얼마로 할지와 "거부되면 그 tick을 통째로 스킵할지"는 미정이다.
3. **역할별 풀 크기 실측값** (3.5절). 표의 값은 초안이다. 0단계에서 역할별 실제 커넥션 사용량을 측정한 뒤 확정한다.

### 닫힌 질문

- ~~**Redis 없이 갈 수 있는가.**~~ **Redis를 쓴다.** `UNLOGGED TABLE` 안도 검토했으나, 캐시 갱신은 몰라도 **틱 팬아웃**이 걸린다 — `LISTEN/NOTIFY`는 커밋 시점에만 발행되어 비트랜잭션 이벤트에 맞지 않고(3.2절), 그렇다고 각 프로세스가 폴링하면 지연이 그대로 손절 지연이 된다.
- ~~**백테스트 잡 큐를 PostgreSQL로 시작할지 Celery로 갈지.**~~ **잡 큐를 두지 않는다.** 목표를 "프로세스를 늘릴 수 있게"로 한정하면서 임계 경로에서 뺐다 ([04](04-async-jobs.md) 2장).
