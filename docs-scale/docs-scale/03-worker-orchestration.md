# 확장판 03 — 자동매매 워커 분산

**상태**: 설계 초안
**원본 대비**: [`docs/features/07-auto-trading.md`](../docs/features/07-auto-trading.md) **4장(백엔드 실행 구조)을 대체**한다. 같은 문서의 1·2·3장(슬롯 구조·잔고 검증·화면), 4.1(시장가 원칙), **4.2(청산과 포지션 경계)**, 5장(FR-M10 잠금), 6~9장은 무수정으로 유효하다.
**해결하는 문제**: [00-architecture](00-architecture.md) 1장의 결합점 ① + tick 예산 초과

---

## 1. 무엇이 문제였나

현재 워커는 `main.py`의 APScheduler 잡 하나다.

```python
for slot_id in _load_active_slot_ids():   # 활성 슬롯 전체를 직렬로
    process_slot(slot_id)
```

문제가 셋이다.

1. **`max_instances=1`은 한 프로세스 안에서만 유효하다.** 프로세스를 늘리면 같은 슬롯을 두 워커가 동시에 평가해 중복 주문이 나간다.
2. **10초 안에 못 끝내면 `coalesce=True`가 tick을 통째로 건너뛴다 — 로그 한 줄 없이.** 일부 슬롯이 조용히 평가를 거른다.
3. **tick 중에 Upbit REST를 부른다.** `candles_service.get_confirmed_candles()`가 캐시 미스면 그 자리에서 HTTP를 친다. 캔들 캐시는 `(symbol, interval)` 단위로 공유되지만, **봉 경계 직후에는 그 조합 수만큼 순차 호출이 발생**한다. 서로 다른 코인 50종에 1분봉을 걸면 매 분 정각에 50회 × 0.27초 ≈ 13.5초로 tick 예산을 넘긴다.

## 2. 샤드 점유

### 2.1 구조

- 샤드 키: **`user_id`**, `user_id % SHARD_COUNT` ([00-architecture](00-architecture.md) 3.1절)
- `SHARD_COUNT`는 **고정 상수**다. 프로세스 수와 무관하며 바뀌면 재해싱이 일어나므로 함부로 조정하지 않는다 (초안 16, [00-architecture](00-architecture.md) 5장 열린 질문 1).
- 워커 프로세스는 기동 시 샤드 0..N-1을 순회하며 `pg_try_advisory_lock(WORKER_NS, shard_id)`로 **잡히는 것을 전부 점유**한다.
- 프로세스가 죽으면 세션이 끊기며 락이 자동 해제되고, 다른 프로세스가 다음 재시도 주기에 집어간다. 별도 하트비트 만료 로직이 필요 없다.
- 프로세스를 추가하면 이미 점유된 샤드는 못 잡으므로 자연히 남은 것만 가져간다. 재균형은 "주기적으로 못 잡은 샤드를 다시 시도"하는 루프 하나로 끝난다.

tick 1회는 **자기가 점유한 샤드에 속한 활성 슬롯만** 순회한다.

```sql
SELECT id FROM strategy_slots
WHERE is_active AND (user_id % :shard_count) = ANY(:owned_shards);
```

> **왜 심볼이 아니라 유저인가**는 [00-architecture](00-architecture.md) 3.1절에 있다. 요약하면 슬롯 분포가 심볼로는 절대 균등해지지 않아서(BTC 쏠림) 프로세스를 늘려도 효과가 없기 때문이고, 워커에는 심볼 순서 보장이 애초에 필요 없기 때문이다.
>
> **부수 효과 하나가 중요하다**: `crc32`를 쓰지 않으므로 "Python `zlib.crc32`와 SQL이 같은 값을 내는가"를 맞출 필요가 없다. 나머지 연산은 애플리케이션과 DB가 동일하게 계산하므로 위 `WHERE` 절을 그대로 쓸 수 있다. (`matcher`는 여전히 심볼 샤딩이라 이 문제가 남는데, 거기서는 심볼 목록을 앱에서 계산해 넘긴다 — [02](02-market-data.md) 4.3절.)

### 2.2 함정 — advisory lock은 **세션** 단위다

SQLAlchemy 커넥션 풀이 커넥션을 반납·재활용하면 락이 풀린다. 샤드 점유는 풀에서 꺼낸 커넥션으로 하면 안 되고, **역할별 전용 커넥션 하나를 프로세스 수명 내내 붙잡고** 유지해야 한다.

이걸 놓치면 증상이 고약하다 — 기동 직후에는 정상이다가 풀이 커넥션을 재활용하는 순간 두 프로세스가 같은 샤드를 동시에 점유하고, **중복 주문이 나가기 시작한다.** 락 획득 후 `SELECT pg_advisory_lock_owner()` 상당의 자체 점검을 주기적으로 돌려 소유를 재확인할 것.

### 2.3 샤딩이 보장하지 않는 것

**한 유저의 슬롯이 두 워커에서 동시에 평가되지 않는다** — 보장하는 건 이것뿐이다.

**자금 정합성은 보장하지 않는다.** 유저 A의 슬롯이 전부 같은 샤드에 모여도, matcher(심볼 샤드)가 A의 지정가 주문을 체결하고 api 프로세스가 A의 수동 주문·입출금을 처리한다. 셋이 같은 `balances` 행을 동시에 노린다 — 자세한 이유는 [00-architecture](00-architecture.md) 3.1.1절. [`docs/features/09-execution-engine.md`](../docs/features/09-execution-engine.md) 3.4절 잠금 순서 규칙을 그대로 지켜야 한다.

### 2.4 샤드를 점유할 때 그리드 라인을 재조정한다

6장의 "체결 후처리 2트랜잭션 분리"를 실제로 막는 장치다. **분산에서 이게 없으면 배포할 때마다 그리드 배정액이 초과될 수 있다.**

#### 무엇이 깨지는가

[`worker.py`](../backend/app/strategy_engine/worker.py)의 `_execute_intent`는 두 번 커밋한다.

```
_place_buy(...)          → 체결 + state.position 커밋   ← 여기서 죽으면
_write_grid_lines(...)   → 라인 점유 표시 별도 커밋      ← 이게 안 돈다
```

라인이 비어 있는 걸로 남으므로 **다음 봉에 같은 라인을 또 매수한다.** 포지션은 이미 있는데 라인은 비어 있으니, 그리드에 배정한 금액을 넘겨 산다.

원본에서는 "프로세스가 죽는" 게 드문 사고였다. 분산에서는 배포·크래시·샤드 재균형이 전부 이 창을 여는 일상적 사건이 된다.

#### 불변식과 복구

그리드 슬롯에는 다음이 성립해야 한다.

> `Σ lines[].quantity` == `state.position.quantity`

워커가 샤드를 점유하면, 그 샤드의 활성 그리드 슬롯마다 이 식을 검사한다.

| 상태 | 의미 | 처리 |
|---|---|---|
| 같다 | 정상 | 통과 |
| `position` > `Σ lines` | 라인 기록이 유실됨 (위 크래시) | 그 슬롯의 체결된 auto 매수 주문을 `filled_at` 역순으로 읽어, **체결가에 가장 가까운 빈 라인**에 그 수량을 기록한다. 차액이 메워질 때까지 반복 |
| `position` < `Σ lines` | 라인에 있는데 포지션이 없음 | 초과분 라인을 빈 상태로 되돌린다 (수동 매도로 사라진 경우 — 자금 위험 없음) |
| 복구 후에도 안 맞음 | 설명되지 않는 불일치 | **슬롯을 OFF하고 경고를 남긴다.** 추측으로 자금을 움직이지 않는다 |

**이 방식이 맞는 이유는 위험이 열리는 순간과 복구가 도는 순간이 정확히 같기 때문이다.** 크래시·배포·재균형은 전부 다른 프로세스의 샤드 점유를 일으키는 사건이고, 점유가 곧 복구 트리거다.

#### 기존 패턴의 재사용이다

새 발상이 아니다. 슬롯 ON 경로의 `_reconcile_phantom_position`([`services/strategy_slots.py`](../backend/app/services/strategy_slots.py))이 `state.position`을 실제 `holdings`에 맞춰 낮추는 것과 **정확히 같은 모양**이다 ([`docs/features/07-auto-trading.md`](../docs/features/07-auto-trading.md) 4.2절). 그 함수가 `state.position`에 하는 일을 `state.grid.lines`에 하는 것뿐이며, 스키마 변경도 주문 경로 수정도 없다.

> **더 엄밀한 대안**: `orders`에 멱등성 키 컬럼을 추가하고 라인을 선점한 뒤 주문하면 exactly-once가 된다. 이 프로젝트 규모에는 과하다고 보고 채택하지 않는다 — 위 재조정은 크래시와 복구 사이의 창에서만 초과 매수를 허용하는데, 그 창이 샤드 점유 주기로 닫힌다.

#### DCA도 같은 창을 갖는다 — 그리고 더 급하다

`_try_dca`도 `_place_buy` 뒤에 `_write_dca_state`를 **별도로 커밋**한다. 크래시하면 `state.dca.next_buy_at`이 안 밀려서 다음 tick에 또 산다.

**그리드보다 급한 이유**: 그리드는 다음 확정봉을 기다리지만(`claim_candle`이 봉당 1회로 묶는다), **DCA는 확정봉 경로를 타지 않으므로**(3.1절) 10초 뒤 다음 tick에 바로 중복 매수가 나간다.

재조정 규칙:

> `next_buy_at` 이후에 체결된 auto 매수 주문이 있으면, 그 매수는 이미 일어난 것이다 — `next_buy_at`을 그 주문 기준으로 밀어준다.

## 3. tick 실행 규칙 (원본 4장의 미문서화 규칙 정식화)

아래는 현재 `strategy_engine/worker.py`에 구현돼 있지만 **어느 설계 문서에도 없던** 규칙들이다. 분산에서는 이걸 모르고 재구현하면 즉시 깨지므로 여기서 정식 기술한다.

### 3.1 슬롯 1개의 tick 처리 순서

```
process_slot(slot_id):
  1. 청산 판정 (손절·익절) — 실시간 현재가로. 확정봉을 기다리지 않는다
     └─ 청산이 일어났으면 이번 tick은 여기서 종료
        (방금 판 포지션을 같은 tick에 도로 사는 것을 막는다)
  2. strategy_type == 'dca' 이면 → DCA 전용 경로 (_try_dca), 종료
  3. 그 외 → 신호 평가 (확정봉 선점 후)
```

- **청산이 신호 평가보다 먼저다.** 포지션을 지키는 일이 새 진입보다 급하다.
- **DCA는 확정봉 경로를 타지 않는다.** 시간 스케줄(`state.dca.next_buy_at`)로 트리거되므로 봉 선점에 묶으면 봉 하나당 한 번밖에 평가되지 않아 예정 시각을 맞출 수 없다.

### 3.2 확정봉 선점은 주문 **전에** 별도 트랜잭션으로 커밋한다

같은 봉을 여러 tick이 반복 평가하면 같은 신호로 중복 주문이 나간다. 그래서 `slot_state.claim_candle`로 봉을 선점한 뒤에만 평가한다.

**선점은 주문보다 먼저, 독립된 짧은 트랜잭션으로 커밋한다.** 주문 경로(`create_order` → `fill_order` → 체결 후처리)가 같은 슬롯 행의 `state.position`을 갱신하므로, 워커가 슬롯 행 잠금을 쥔 채 주문하면 교착하거나 tick이 멈춘다.

> **워커는 주문 중에 슬롯 행 잠금을 쥐지 않는다.** 이건 성능 최적화가 아니라 교착 회피다.

분산에서도 동일하다. `claim_candle`의 조건부 갱신이 **샤드 소유권과 무관하게** 중복 평가를 막는 두 번째 방어선이므로, 샤드 재균형 중 잠깐 두 프로세스가 같은 슬롯을 보더라도 주문은 한 번만 나간다.

### 3.3 체결 훅에서 하면 안 되는 것

`matcher._apply_auto_trading_hook`에서 `notification_settings.get_or_create_settings()`를 쓰면 안 된다 — **내부 `commit()`이 `fill_order` 트랜잭션을 끊는다.** `db.get`으로 직접 읽어야 한다.

일반화하면: **체결 트랜잭션 안에서 호출하는 어떤 함수도 스스로 커밋해서는 안 된다.** 체결·잔고·보유수량·슬롯 state는 한 트랜잭션에서 원자적으로 확정돼야 한다.

### 3.4 슬롯 단위 예외 격리

슬롯 하나의 실패가 나머지를 막지 않도록 슬롯 단위로 예외를 삼키고 로그만 남긴다. 이 방침은 유지하되, 확장판에서는 **삼킨 예외를 관측 지표로 집계**한다 ([06](06-observability.md)) — 지금은 로그로만 흘러가 아무도 안 본다.

## 4. `state` JSONB 소유권 — 분산에서는 필수다

> 이 절은 현재 [`backend/app/services/slot_state.py`](../backend/app/services/slot_state.py) 파일 헤더에만 존재하는 설계를 정식 문서로 옮긴 것이다. **문서만 보고 재구현하면 반드시 read-modify-write로 만들게 되고, 그 순간 경합이 재발한다.**

### 4.1 누가 어떤 키를 쓰는가

| 키 | 쓰는 주체 |
|---|---|
| `state.position` | 체결 후처리(`matcher._apply_auto_trading_hook`)만 |
| `state.last_evaluated_candle_at`, `state.grid.*`, `state.dca.*` | 워커만 |

**`state.position`의 유일한 예외**: 슬롯 ON 경로(`strategy_slots._reconcile_phantom_position`)가 실제 `holdings`와 어긋난 포지션을 낮춰 쓴다 ([`docs/features/07-auto-trading.md`](../docs/features/07-auto-trading.md) 4.2절). 그 경로는 `balances` 행을 `FOR UPDATE`로 잡은 뒤 실행되고 모든 체결도 같은 행을 잠그므로, 체결과 동시에 실행될 수 없다.

### 4.2 왜 `jsonb_set`이어야 하는가

Python에서 `slot.state`를 통째로 읽어 dict를 고치고 다시 대입하는 방식(read-modify-write)은, 읽은 시점과 쓰는 시점 사이에 다른 주체가 **자기 키**를 갱신했으면 그 변경을 통째로 덮어써 잃는다.

그래서 모든 쓰기를 PostgreSQL `jsonb_set` / `-`(키 삭제) 연산으로 **자기 키만** 갱신한다. 슬롯 행에 배타 잠금을 걸지 않고도 서로의 키를 건드릴 수 없게 만드는 방식이며, 워커가 잠금을 쥔 채 주문하다 체결 경로와 교착하는 것도 함께 피한다 (3.2절).

**분산에서 이게 왜 결정적인가**: 단일 프로세스에서는 워커 tick과 체결 후처리가 같은 프로세스의 다른 스레드였다. 프로세스가 갈라지면 애플리케이션 수준의 어떤 락도 통하지 않으므로, **DB 연산 자체가 부분 갱신이어야만** 한다. 이 설계는 이미 분산 대비가 되어 있다.

### 4.3 커밋 책임의 비대칭 (중요)

| 함수 | 커밋 | 이유 |
|---|---|---|
| `claim_candle` | **스스로 커밋한다** | 워커의 독립된 짧은 트랜잭션 (3.2절) |
| `write_position` | **커밋하지 않는다** | `fill_order`가 체결·잔고·보유수량과 같은 트랜잭션에서 원자적으로 커밋해야 한다 (3.3절) |

## 5. tick 예산 지키기

### 5.1 워커 tick에서 Upbit REST 호출을 제거한다

가장 큰 변경이다.

| | 현재 | 확장판 |
|---|---|---|
| 캔들 조회 | 워커가 tick 중에 `get_confirmed_candles()` → 캐시 미스면 그 자리에서 Upbit HTTP | 워커는 **DB 캐시만 읽는다** |
| 캐시 채우기 | 조회 시점에 우연히 | `scheduler` 역할이 미리 채운다 ([04](04-async-jobs.md) 3장) |
| 캐시 미스 시 | 블로킹 HTTP (0.27초 × 조합 수) | **이번 tick 평가를 건너뛰고 기록한다** |

캔들이 없어서 건너뛴 것은 **반드시 관측 지표로 남긴다.** 지금은 흔적이 없어서 "왜 신호가 안 났지"를 추적할 방법이 없다.

`scheduler`가 채워야 할 대상은 "활성 슬롯이 쓰는 `(coin_symbol, interval)` 조합"이고, 이건 `strategy_slots`에서 바로 뽑을 수 있다.

### 5.2 예산 초과를 조용히 넘기지 않는다

- 샤드별 tick 소요 시간을 매번 기록한다.
- `TICK_INTERVAL_SECONDS`(10초)를 넘으면 경고 로그 + `worker_heartbeats` 갱신 ([06](06-observability.md) 2장).
- 관리자 화면에 샤드별 tick 소요·슬롯 수를 노출해 **`SHARD_COUNT`를 올릴 시점을 눈으로 판단**할 수 있게 한다.

## 6. 승계되는 알려진 한계

원본 구현에서 "알지만 안 고침"으로 남긴 것들이다. 확장판에서 상태가 달라지므로 재평가 결과를 함께 적는다.

| 한계 | 원본에서의 판단 | 확장판에서 |
|---|---|---|
| **워커 다중 intent 부분 실패** — 그리드 여러 라인 중 하나에서 예외가 나면 나머지 라인은 이번 봉에서 유실 (`claim_candle`이 선점 완료) | 라인이 empty로 남아 다음 봉에 재시도되므로 self-healing. 영향 낮아 방치 | **그대로 방치.** 분산이 이 성질을 악화시키지 않는다 |
| **체결 후처리 2트랜잭션 분리** — `_place_buy`(체결·position 커밋) → `_write_grid_lines`/`_write_dca_state`(별도 커밋) 사이에 프로세스가 죽으면 라인/DCA 진행 상태만 뒤처짐 (그리드는 같은 라인 재매수 → 배정액 초과 가능) | `create_order`가 내부 커밋을 하는 구조라 한 트랜잭션으로 묶으려면 주문 경로 전반을 손봐야 해 보류 | **2.4절 재조정으로 해결.** 트랜잭션 분리 자체는 그대로 두되, 샤드 점유 시점에 `state.grid.lines`·`state.dca.next_buy_at`을 체결 기록에서 재구성한다. 위험이 열리는 사건(크래시·배포·재균형)이 곧 복구 트리거라 창이 자동으로 닫힌다 |
| **수수료 정밀도** — `orders.fee`는 4자리 quantize인데 `_apply_balance`는 무반올림 계산식으로 차감 (실측 22건 중 19건이 최대 0.00005원 차이) | 저장 fee를 쓰게 바꾸면 취득원가·실현손익·백테스트 공유 함수까지 연쇄 수정이라 docstring 명시만 | **그대로.** 단, 손익을 거래내역으로 재구성할 때는 `orders.fee` 합이 아니라 계산식을 써야 한다는 점을 관리자 통계([05](05-admin.md) 3장)에서도 지켜야 한다 |
| **슬롯 OFF 중 수동 매도 → stale position** | 재ON 시 `_reconcile_phantom_position`이 보정 (4.1절 예외) | 그대로 유효. 보정 경로가 `balances` 잠금 안에서 도는 것이 분산에서도 안전 근거 |

## 7. 검증 방법

1. **단일 샤드 회귀**: `SHARD_COUNT=1`, 워커 프로세스 1개 → 기존 pytest 스위트 전부 통과 (현재 동작과 동일해야 함)
2. **샤드 분할**: `SHARD_COUNT=4`, 워커 프로세스 2개 → 슬롯이 정확히 한 번씩만 평가되는지 (같은 슬롯에 중복 주문이 없는지)
3. **페일오버**: 워커 프로세스 하나를 `SIGKILL` → 남은 프로세스가 그 샤드를 집어가고 tick이 이어지는지
4. **커넥션 풀 함정(2.2절)**: 풀 크기를 1로 줄이고 장시간 기동해 락이 유지되는지
5. **캔들 미스 처리**: `candles` 테이블을 비우고 워커가 블로킹 없이 스킵 + 기록하는지
6. **tick 예산**: 슬롯을 인위적으로 늘려 10초를 넘겼을 때 경고가 실제로 남는지 (조용히 넘어가지 않는지)
7. **그리드 재조정(2.4절)**: `_place_buy` 직후 `_write_grid_lines` 직전에 프로세스를 죽이고, 다른 워커가 샤드를 집어갈 때 라인이 복구되는지. **복구 없이 다음 봉을 넘기면 같은 라인을 재매수하는지**를 먼저 확인해 재현부터 잡을 것
8. **DCA 재조정(2.4절)**: 같은 방식으로 `_write_dca_state` 직전에 죽이고, 다음 tick에 중복 매수가 나가지 않는지 (그리드보다 빨리 터지므로 재현이 쉽다)
9. **샤드 분포**: 유저를 인위적으로 늘려 샤드별 슬롯 수 편차를 확인. 심볼 샤딩이었다면 쏠렸을 구성(전원 BTC 슬롯)에서 균등하게 퍼지는지가 키 변경의 판정 기준이다
