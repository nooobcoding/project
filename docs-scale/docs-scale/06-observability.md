# 확장판 06 — 관측

**상태**: 설계 초안
**원본 대비**: 신규. 대응하는 기존 문서가 없다.

---

## 1. 왜 이게 먼저인가

확장판에서 **가장 먼저 만들어야 할 것**이 이것이다. 다른 문서들이 정의하는 변경은 전부 "무너지는 지점"을 옮기는 일인데, **지금은 그 지점이 어디인지 측정할 방법이 없다.**

구체적으로 현재 눈에 안 보이는 것들:

| 안 보이는 것 | 어떻게 새는가 |
|---|---|
| 워커 tick이 10초를 넘겼는지 | APScheduler `coalesce=True`가 **로그 한 줄 없이** 실행을 건너뛴다. 일부 슬롯이 조용히 평가를 거른다 |
| 슬롯 처리 중 삼킨 예외 | `logger.exception`으로 흘러가고 아무도 안 본다 |
| 캔들이 없어 평가를 건너뛴 횟수 | 흔적 자체가 없다 ([03](03-worker-orchestration.md) 5.1절에서 신설) |
| Upbit 호출량·429 발생 | 없음 |
| 백테스트가 워커를 굶기고 있는지 | 없음 |
| 프로세스가 커넥션을 몇 개나 쓰는지 | [`database.py`](../backend/app/database.py)에 풀 설정이 없어 기본값(최대 15)이 그대로 적용되는데, 실제 사용량을 아무도 모른다. 프로세스를 늘리는 순간 이게 상한이 된다 ([00](00-architecture.md) 3.5절) |

**0단계로 이걸 붙이면 현재 코드에도 그대로 쓸 수 있다** — 프로세스를 쪼개기 전에 "우리 시스템이 지금 몇 명·몇 슬롯에서 무너지는가"를 실측할 수 있고, 그 숫자가 [00-architecture](00-architecture.md) 5장의 열린 질문(`SHARD_COUNT`, `PRICE_MAX_AGE_SECONDS`)에 답을 준다.

## 2. `worker_heartbeats` 테이블

프로세스·역할·샤드 단위의 최신 상태 1행씩. 시계열이 아니라 **현재 상태 스냅샷**이다 (시계열이 필요해지면 그때 별도 테이블).

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGSERIAL PK | |
| role | VARCHAR(20) | `worker` / `matcher` / `market-data` / `scheduler` |
| shard_id | SMALLINT NULL | 샤드 역할만 |
| process_id | VARCHAR(64) | 호스트명+PID 등 식별자 |
| last_tick_at | TIMESTAMPTZ | 마지막 tick 시작 시각 |
| last_duration_ms | INT | 마지막 tick 소요 |
| max_duration_ms | INT | 관측 이래 최대 (리셋 가능) |
| over_budget_count | INT | 예산 초과 누적 횟수 |
| item_count | INT | 처리 대상 수 (워커=슬롯 수, matcher=DB 조회한 틱 수) |
| db_connections | INT | 이 프로세스가 실제로 쓴 커넥션 수 (풀 체크아웃 최대치) — [00](00-architecture.md) 3.5절 예산 실측용 |
| error_count | INT | 삼킨 예외 누적 |
| skip_count | INT | 캔들 없음 등으로 건너뛴 횟수 |
| updated_at | TIMESTAMPTZ | |

`UNIQUE (role, shard_id, process_id)`. 매 tick 끝에 UPSERT한다.

> **쓰기 비용 주의**: 10초마다 샤드 수만큼 UPSERT면 무시할 만하다. 하지만 `matcher`는 틱마다 도므로 **매 틱 UPSERT하면 안 된다** — N초에 한 번으로 묶어서 쓴다.

## 3. 최소 지표 세트

### 3.1 워커

| 지표 | 경고 조건 |
|---|---|
| tick 소요 시간 | `> TICK_INTERVAL_SECONDS`(10초) |
| 샤드별 활성 슬롯 수 | 샤드 간 편차가 크면 `SHARD_COUNT` 재검토 신호 |
| 캔들 없음 스킵 | 0보다 크면 `scheduler`의 미리 채우기가 밀리고 있다는 뜻 |
| 삼킨 예외 | 증가 추세면 조사 |

### 3.2 시세

| 지표 | 경고 조건 |
|---|---|
| 마지막 틱 수신 후 경과 | `> PRICE_MAX_AGE_SECONDS` — market-data가 죽었거나 페일오버 중 ([02](02-market-data.md) 3.3절) |
| matcher가 DB를 실제로 조회한 비율 | `pending_symbols` 힌트가 잘 듣고 있는지 ([02](02-market-data.md) 4.2절) |

### 3.3 외부 호출·백테스트

| 지표 | 경고 조건 |
|---|---|
| Upbit 토큰 잔량 / 429 발생 수 | 429가 나오면 버킷 리필 속도를 낮춘다 ([04](04-async-jobs.md) 3.2절) |
| `scheduler` 캔들 채우기 소요 | 봉 주기를 넘기면 워커 스킵으로 이어진다 ([04](04-async-jobs.md) 3.3절) |
| 백테스트 세마포어 대기 시간 | 대기가 60초 타임아웃에 닿기 시작하면 잡 큐 재검토 신호 ([04](04-async-jobs.md) 2.4절) |

### 3.4 샤드 커버리지 — 빈 샤드를 잡는다

**나머지 지표와 성격이 다르다. 이건 "무엇이 느린가"가 아니라 "무엇이 아예 없는가"를 본다.**

`worker_heartbeats`는 **살아 있는 프로세스만** 행을 남긴다. 그래서 아무도 점유하지 않은 샤드는 **행 자체가 생기지 않고, 결과적으로 아무 경고도 나지 않는다.** 모든 지표가 초록인데 그 샤드에 속한 유저의 자동매매는 통째로 멈춰 있는 상태가 가능하다.

| 역할 | 빈 샤드가 생기면 |
|---|---|
| `worker` | 그 샤드 유저들의 슬롯이 평가되지 않는다 — **손절·익절이 안 돈다** |
| `matcher` | 그 샤드 심볼의 지정가 주문이 영영 체결되지 않는다 |

둘 다 사용자에게는 "왜 안 되지?"로만 보이고 서버에는 아무 오류가 없다. 5장의 조용한 실패 금지 규칙에 정면으로 걸린다.

**검사 주체는 `scheduler`다.** 주기적으로 역할별 점유 샤드 집합과 `0..SHARD_COUNT-1`을 비교한다.

```
누락 = {0..SHARD_COUNT-1} - {점유된 샤드}
누락이 비어 있지 않으면 → 경고 로그 + 관리자 화면 노출
```

| 지표 | 경고 조건 |
|---|---|
| 역할별 미점유 샤드 수 | **0보다 크면 즉시 경고.** 재균형 중 잠깐 뜨는 건 정상이므로, 연속 N주기(초안 3회) 이상 지속될 때만 경고한다 |
| 샤드별 마지막 tick 경과 | 점유는 돼 있는데 tick이 안 도는 경우 — 락은 잡고 죽지 않은 프로세스 |

> **두 번째 행이 첫 번째보다 미묘하다.** advisory lock은 세션이 살아 있으면 유지되므로, 프로세스가 멈춰 있어도(데드락·무한 대기) 락은 안 풀린다. 그러면 샤드는 "점유됨"으로 보이는데 실제로는 아무 일도 안 일어난다. `last_tick_at`이 예산의 몇 배를 넘으면 이 상태다.

## 4. 노출 경로

1. **로그** — 경고 조건 충족 시 `logger.warning`. 조용한 실패를 없애는 최소선.
2. **관리자 화면** — [05](05-admin.md) 3-D. `worker_heartbeats`를 그냥 조회해 표로 보여준다.
3. **`GET /health` 확장** — 역할별 생존 여부. 배포·오케스트레이션이 쓸 수 있게.

> Prometheus·Grafana는 도입하지 않는다. 테이블 하나 + 관리자 화면으로 충분하고, 운영 대상을 늘리지 않는 편이 이 규모에 맞다. 필요해지면 `worker_heartbeats`를 exporter로 노출하는 것이 자연스러운 다음 걸음이다.

## 5. 조용한 실패 금지 규칙

확장판 코드 전반에 적용하는 규칙이다.

1. **예외를 삼키는 모든 곳은 카운터를 올린다.** `except Exception: logger.exception(...)`만 있는 코드는 금지 — 반드시 `error_count`도 증가시킨다.
2. **건너뛰기는 전부 기록한다.** 캔들 없음, 시세 stale, 잔고 부족, 봉 선점 실패 — 각각 왜 건너뛰었는지 구분 가능해야 한다.
3. **예산 초과는 경고다.** tick이 예산을 넘기면 성공했더라도 경고를 남긴다.

## 6. 검증 방법

1. 슬롯을 인위적으로 늘려 tick을 10초 넘기고, 경고 로그와 `over_budget_count` 증가를 확인
2. `candles` 테이블을 비우고 `skip_count` 증가를 확인
3. `market-data`를 정지시키고 시세 경과 지표가 임계를 넘는지 확인
4. 백테스트를 여러 개 돌리면서 워커 `last_duration_ms`가 변하는지 관찰 — **워커를 별도 프로세스로 분리하기 전후를 비교하면 GIL 격리 효과가 숫자로 나온다** ([04](04-async-jobs.md) 2.1절)
5. **커넥션 실측**: 부하를 준 상태에서 `db_connections`와 `SELECT count(*) FROM pg_stat_activity`를 대조해 [00](00-architecture.md) 3.5절 표의 초안값을 확정
6. **빈 샤드 감지(3.4절)**: 워커 프로세스를 전부 내렸다가 하나만 올려, 점유되지 않은 샤드가 경고로 잡히는지
7. **점유했는데 안 도는 샤드(3.4절)**: 워커 프로세스를 `SIGSTOP`으로 멈춰 락은 유지된 채 tick만 멈춘 상태를 만들고, `last_tick_at` 기반 경고가 뜨는지
